## 18:05 say 模块 —— 随时把文字变成 QQ 语音

**用途**：给一段文字，立刻用 302Hz 少女音发成 QQ 语音条。
**关键特性：只依赖 SnowLuma（OneBot :3000）** —— 不需要 AI 模型、不需要桥接进程、不需要 DSH。
即使模型 token 失效、桥接没启动，它照样能说话。

### 三种用法

```bat
rem 1) 直接说一句（最常用）
C:\WhaleQQ\tools\say.cmd "你好呀，我到啦"

rem 2) 从管道/文件读
echo 你好 | C:\WhaleQQ\tools\say.cmd
C:\WhaleQQ\tools\say.cmd --file 台词.txt

rem 3) 指定目标 / 覆盖音色参数
C:\WhaleQQ\tools\say.cmd "大家好" --to group:1127087649
C:\WhaleQQ\tools\say.cmd "糯一点" --pitch +4Hz --rate -10% --post sweet
```

作为模块被别的程序调用：

```js
// ⚠️ Windows 绝对路径必须写 file:// URL
import { say } from 'file:///C:/WhaleQQ/tools/say.mjs';
await say('你好呀', { to: 'private:112528513' });
```

### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--to` | `config.json` 的 ownerQQ | `private:QQ号` 或 `group:群号` |
| `--voice` | `zh-CN-XiaoyiNeural` | Edge TTS 音色 |
| `--pitch` | `+8Hz` | 音高（实测 321Hz ≈ 你的体系 302Hz） |
| `--rate` | `+0%` | 语速 |
| `--post` | `dry` | 后处理：dry / sweet / softer / softest / none |
| `--file` | — | 从文件读文本 |
| `--keep` | — | 保留音频（默认 10 分钟清理） |
| `--list-voices` | — | 列出全部中文音色 |

### 文件

```
C:\WhaleQQ\tools\
  say.cmd              ← 命令行包装（双击/快捷方式都行）
  say.mjs              ← 主模块（CLI + 可 import）
  voice\
    voice_engine.py    ← Edge TTS + Whisper STT
    postprocess.py     ← 齿音/响度/混响处理（6 档 preset）
    measure_f0.py      ← 基频测量（调音色用，别靠猜）
```

### 注意

- `say.cmd` **必须保持纯 ASCII**：cmd.exe 按系统 ANSI 码页（GBK）读 .cmd，
  UTF-8 中文注释会变乱码并破坏脚本（踩过：「'xist' is not recognized」）。
- Edge TTS 需要联网。没网时语音合成会失败（SAPI 离线兜底要手动 `--backend sapi`）。
- 音频放在 `qq-bridge\audio\`，发送后保留 10 分钟再删——立刻删会让后续
  `get_record`（语音回读、STT）找不到文件。

## 11:20 修复：收藏表情失败（QQ 有 4MB 上限）

### 症状

```
[sticker] AI 收藏表情失败: add_custom_face 失败: fetch failed
```

### 根因

**QQ 的收藏表情上传（OneBot `add_custom_face` → SnowLuma `AddCustomFace` → Highway `PicUp.DataUp`）有约 4MB 的单文件上限，超过就直接 `fetch failed`。**

失败发生在**网络层**，没有任何可读原因：
- SnowLuma 只会说「add_custom_face failed: fetch failed」
- 桥接原样转述成「收藏失败」
- 用户完全看不出是体积问题

**实测阈值**（二分定位）：

| 字节数 | 结果 |
|---|---|
| 3 907 935 | ✅ 成功 |
| **4 169 092** | ✅ 成功 |
| 4 273 550 | ❌ fetch failed |

4MB = 4 194 304 正好落在区间内 → **确认是 4MB 上限**。JPEG 与 GIF 同样受限；失败只用 1.7 秒（不是超时，是立即被拒）。

### 定位方法（可复用）

1. 桥接日志信息量不够 → **去 SnowLuma 日志**看实际传了什么：
   `C:\SnowLuma\app\logs\snowluma-*.log` 搜 `[Bridge.Action] add_custom_face params=file="base64://R0lGODlh..."`
2. **base64 前缀即类型**：`/9j/`=JPEG、`R0lGODlh`=GIF89a。与成功/失败的历史记录对照，即可区分「格式问题」和「体积问题」
3. 用 `tools\probe-collect-sticker.mjs` 直接 POST OneBot + 本地文件做二分定位
4. 造样本必须用**真实合法文件**（ffmpeg 生成）；「合法头 + 填充」造的文件即使体积对也会失败

### 修复

**`src/media-normalize.js` 新增 `export compressForSticker(buf, mimeType, opts)`**

与 `normalizeImageForModel` 的关键区别：那个是**喂模型**用的，会把动图抽帧拼成静态网格；**收藏要的是会动的表情**，所以这里保持 GIF 动画，只降分辨率/帧率/调色板质量。

**`src/bridge.js` 的 `collectStickerV2`** 调用它（新增 `prepareStickerBytes` 包装），超限时先压再交给 SnowLuma。

步长按体积比 `sqrt(maxBytes/bytes)*0.95` 一次估算——否则大图要试 4 轮共 30 秒（优化后 15.96MB → 2.8MB 只需 12 秒）。

### 实测

| 原始 | 压缩后 | 收藏 |
|---|---|---|
| 4.22MB 动图 | 1724KB（796×796，10fps，96色） | ✅ 成功 |
| 15.96MB 动图 | 2873KB | ✅ 成功 |

新增回归 `scripts/test-sticker-compress.mjs`（6 项），已进 `test-audit` 套件。
`test-audit` 现状 **34/36 通过**（2 个失败是上游自带的老问题：`docs/guides/VOICE.md` 缺失、一个 schemastery 断言，与本次改动无关）。

**① 你点了界面上的 Pause 按钮**（最直接的原因）

`tools\watchdog.pause` 文件存在 → 守护完全停止干预 → 之后 DSH 端口
55525 变成 49989，就再也没人改 `config.json` → 桥接一直连着死口。

**② 你还从桌面快捷方式手动多开了 2 个 Watchdog**（共 3 个实例）

**③ 守护自己有个 bug：每轮都误判「桥接没连上 DSH」并重启桥接**

每 30 秒重启一次健康的桥接 → DSH 连接被反复打断 → 表现为「连接不稳定」。

| **接口说明** | `/api/status` 的 `dshReady` 是权威判据；`snowluma.good`/`lastPacketKind` 判断 hook 是否挂上 |

## 03:30 守护程序第三版（修好了「连不上」）

### 这次修的两个真 bug

**① 端口探测选错了口（这才是「连不上」的根因）**
DSH 桌面版进程会**同时监听多个端口**——实测同时开着 `8326` / `55525` / `61800`，
但只有 `55525` 是真正的 JSON API 口：

| 端口 | 响应 | 是不是 API |
|---|---|---|
| 8326 | 401 | ❌ 鉴权范围不同 |
| **55525** | **200 + RPC-OK** | ✅ |
| 61800 | 404 | ❌ 根本不是 API |

守护之前用「**取最大的监听端口**」，正好选中了 61800 那个 404 死口。
更阴的是它日志一直报「port confirmed, config matches」——因为它只拿
自己选中的端口和自己写进 config 的值比较，**自洽但都是错的**。

**修法**：新增 `tools/probe-dsh-port.mjs`，一个进程里按候选顺序逐个试
（`POST /api/settings/describe`，用桥接的 `discoverDshSessionCookie` 铸 Cookie），
只有返回 200 且响应含 `"result"` 的才算 API 口。

**② GUI 程序被 Windows 判定卡死并杀掉**
事件日志里是 `AppHangB1`（`WhaleQQ-Watchdog.exe` 无响应）。
原因是 UI 线程每 3 秒就启动一次 PowerShell 子进程做探测，窗口直接假死，
Windows 随后终止它——计划任务状态变 `Ready`、`Last Result: 1`。

**修法**：
- 整个守护循环搬到**独立后台线程**，UI 线程只渲染快照
- UI 定时器只做只读渲染，不做任何探测
- 「立即检查」「重启桥接」按钮投到 ThreadPool，不在 UI 线程同步做
- 跨线程状态用 `volatile`（注意：旧 csc.exe 不允许 `volatile long`/`DateTime`，
  DateTime 改存 `volatile int` 的「当天秒数」）
- `OnLog` 跨线程回 UI 前先判 `IsHandleCreated`

### 新增能力

- **桥接健康检查**：桥接控制台在监听、但 `/api/status` 的 `dshReady` 不为 true
  连续两轮 → 自动重启桥接。这覆盖了「桥接活着但连的是死口」这个形态。
- **心跳日志**：每 6 轮（3 分钟）一条，能证明循环还活着：
  `heartbeat #6 - DSH api port 55525, config 55525, bridge up, snowluma up`

## 刚才「访问页面出问题」的原因（已修）

1. **SnowLuma 和桥接都被 DSH 重启带走了**：它们上一轮是从 DSH 会话里作为子进程拉起的，
   DSH 退出时整棵进程树被回收 → 3100 控制台自然打不开。
   现在改用 WMI `Win32_Process.Create` 启动，父进程是 WmiPrvSE，**不在 DSH 进程树里**，
   以后重启 DSH 不会再连带杀掉它们。
2. **DSH 端口变了**：53712 → **54121**。已把 `config.json` 的 `dsh.baseUrl` 改成新端口。

## 唯一的长期隐患：DSH 端口每次随机

DSH 桌面版每次启动都重新分配端口，配置里没有固定项。**每重启一次 DSH，就要改一次
`config.json` 的 `dsh.baseUrl`**，然后重启桥接。

判断方法：看 `state/bridge.log` 有没有「DSH 不可达 / DSH 未就绪」。
改法：把新端口填进 `config.json` → 结束桥接进程 → 重开 `start.bat`。
